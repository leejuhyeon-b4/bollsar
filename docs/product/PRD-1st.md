# 애배력 PRD 초안

작성일 2026년 8월 12일 · 버전 0.1

---

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 이름 | 애배력 |
| 한 줄 설명 | 애배 최대 4명의 출연 회차와 캐스팅, 이벤트 정보를 한 달력에서 보고 내 관람 일정으로 담아두는 서비스 |
| 유형 | PC 우선 반응형 웹 |
| 난이도 | 중급~상급 |
| 개발 기간 | 4~6주 |

난이도를 중급이 아닌 중급~상급으로 잡은 이유는 로그인, 데이터베이스, 제보 검수 흐름이 모두 들어가는데 백엔드 구현이 처음이기 때문이다. 화면 자체의 복잡도는 높지 않다.

## 2. 사용자 시나리오

### 누가

애배가 2명 이상 있고 월 2~3회 이상 관람하는 20~30대 관객. 특정 배우를 따라 같은 작품을 반복 관람하는 성향이 있다.

**대상이 아닌 사람**을 명시해둔다. 연 3~4회 관람하고 배우가 아니라 작품을 보고 고르는 라이트 관객은 애배 4명을 채우지 못한다. 이들을 포함하려 하면 애배 중심 설계 자체가 흔들린다.

### 언제

| 순위 | 시점 | 하는 일 |
| --- | --- | --- |
| 1 | 월간 캐스팅표 공개일 | 애배가 언제 오르는지 훑고 갈 회차를 가늠 |
| 2 | 티켓 오픈 직전 | 원하는 캐스팅 조합이 있는 날짜를 추림 |
| 3 | 관람 며칠 전 | 그날 커튼콜 촬영이나 포토타임이 있는지 확인 |
| 4 | 관람 당일 | 대체 캐스팅이 떴는지 확인 |

1순위가 캐스팅표 공개일이라는 것은 **데이터 반영 속도가 곧 경쟁력**이라는 뜻이다. 기존 서비스보다 늦게 올라오면 쓸 이유가 없다.

### 왜

지금은 제작사 공지 이미지, 트위터, 예매처를 오가야 하고 회차별 이벤트 정보는 어디에도 정리되어 있지 않다.

### 경쟁 서비스

| 서비스 | 하는 것 | 안 하는 것 |
| --- | --- | --- |
| 뮤연 | 날짜별 캐스팅 달력, 배우·작품 검색, 관심 저장, 관람 기록. KOPIS 기반, 무료, 로그인 없음 | 회차별 이벤트 정보, 유저 제보, 캐스팅 변경 이력, 캐스팅 조합 필터, 계정 동기화 |
| 뮤킷 | 당일 공연 일정과 캐스팅 | 위와 대체로 동일 |
| 티팅타임 | 티켓 오픈 알림 | 캐스팅 스케줄 |

**애배력의 차별점은 회차별 이벤트 정보와 유저 제보 커뮤니티다.** 캐스팅 달력 자체는 이미 존재한다.

## 3. 핵심 기능 목록

### 필수 기능

1. 배우·작품 통합 검색 (약칭 인식)
2. 배우 상세 — 출연 작품 칩 필터 + 월간 달력
3. 작품 상세 — 배역별 배우 칩 필터 + 월간 달력
4. 회차 상세 — 작품, 일시, 장소, 배역별 캐스팅, 이벤트
5. 애배 등록 (최대 4명)
6. 애배 달력 — 배우 칩 필터
7. 내 달력 — 예매 완료 회차 담기·빼기
8. 이벤트 정보 제보
9. 캐스팅 오류 정정 제보
10. 제보·공지 피드 (홈)
11. 캐스팅 변경 이력 보관 및 표시
12. 로그인 (이메일 기반)

### 선택 기능 (배포 후 안정화 이후)

- 캐스팅표 공개 알림, 티켓 오픈 알림
- 외부 캘린더 내보내기 (ICS)
- 별칭 사전 관리 화면
- 관람 기록 아카이브

### MVP 제외

- 관람 기록 — 차별점과 거리가 있고 경쟁 서비스가 이미 제공
- 관리자 화면 — Supabase 대시보드의 테이블 편집기로 대체
- 알림 전반 — 계정·푸시 권한 구현 부담

## 4. 기술 스택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js (App Router) | Vercel과 같은 회사가 만들어 배포가 단순 |
| 언어 | TypeScript | 바이브코딩 시 AI가 짠 코드의 오류를 편집기가 먼저 잡아줌 |
| 스타일 | Tailwind CSS | 프로토타입과 동일, 학습 자료 풍부 |
| 인증·DB | Supabase (Auth + Postgres) | 로그인과 DB를 한 번에 해결, 무료 구간 충분 |
| 배포 | Vercel | Next.js와 통합 |
| 데이터 입력 | Supabase 테이블 편집기 | 관리자 화면을 만들지 않아 작업량 대폭 절감 |

**2단계로 미루는 것**: KOPIS 오픈 API 연동과 자동 수집 배치. KOPIS는 공연법에 근거한 공공 데이터라 이용에 법적 부담이 없지만, 회차별 캐스팅을 제공하지 않아 핵심 데이터를 채워주지 못한다. 자동화를 먼저 붙이면 어려운 일을 먼저 하면서 정작 캐스팅 데이터는 비어 있는 상태가 된다.

## 5. 화면 구성

### 페이지

| 탭 | 이름 | 로그인 | 내용 |
| --- | --- | --- | --- |
| 1 | 홈 (제보·공지) | 불필요 | 상단 검색창 + 제보 반영·캐스팅 변경·캐스팅표 공개 피드 |
| 2 | 검색하기 | 불필요 | 검색란, 선택 후 칩 필터와 달력 |
| 3 | 내 달력 | **필요** | 예매 완료 회차 월간 달력 |
| 4 | 애배 달력 | **필요** | 애배 4명 전체 회차 월간 달력 |

홈을 제보·공지로 둔 이유는 알림 기능이 없기 때문이다. "무엇이 바뀌었는지"를 보여줄 자리가 여기밖에 없다. 다만 첫 방문자가 공지 목록만 보면 서비스를 이해하지 못하므로 **홈 최상단에 검색창을 둔다.** 검색어를 입력하면 검색 페이지로 이동한다.

### 비로그인 처리

내 달력과 애배 달력 탭은 **비로그인 상태에서도 노출**하되, 누르면 로그인 유도 화면을 보여준다. 로그인 버튼만 두지 않고 무엇을 할 수 있는지 설명 문구와 흐린 미리보기를 함께 배치한다.

### 반응형

모바일에서도 월간 달력 형태를 유지한다. 다만 셀 폭이 좁아지므로 다음 규칙을 적용한다.

- 셀 안에는 시간만 표시하고 작품 약칭은 생략한다
- 작품·배우 구분은 색으로만 한다
- 하루 회차가 3개를 넘으면 `+N`으로 접는다
- 셀을 탭하면 상세가 열려 텍스트로 확인 가능하게 한다

## 6. 상세 기능 명세

### 6.1 검색

- 배우 이름과 작품명을 하나의 입력창에서 받는다
- 작품은 정식 명칭과 별칭 모두로 검색된다 (예: 붉은 편지 = 붉편)
- 대상을 선택하기 전에는 검색란만 노출한다
- 선택하면 배우 뷰 또는 작품 뷰로 전환된다

### 6.2 배우 뷰

- 그 배우가 출연 중인 작품이 원형 칩으로 표시된다
- 칩은 토글식 고정 필터이며, 아무것도 선택하지 않은 상태가 전체 보기다
- 여러 칩 선택 시 **합집합**으로 동작한다 (한 회차는 한 작품에만 속하므로)
- 달력 셀 색은 작품별로 구분된다 (칩 색과 동일)
- `+ 애배로 추가하기` 버튼을 함께 배치한다

### 6.3 작품 뷰

- 출연 배우가 원형 칩으로 표시되며 **배역마다 줄을 바꾼다**
- 필터 규칙
  - **배역이 다른 칩끼리는 교집합**: 윤서 유하람 + 해강 강태윤 → 두 사람이 함께 오르는 회차만
  - **같은 배역 안에서는 합집합**: 윤서 유하람 + 윤서 백지운 → 둘 중 누구든 나오는 회차
- 달력 셀 색은 처음으로 필터가 걸린 배역의 배우 기준으로 칠한다
- 필터를 걸지 않은 상태에서는 첫 배역(주연) 배우 기준으로 칠한다
- **결과가 0건일 때 빈 달력을 보여주지 않고 안내 문구를 띄운다.** "고정한 배우가 모두 함께 오르는 회차가 없습니다" — 이 정보 자체가 유저에게 가치가 있다

### 6.4 회차 상세

달력에서 특정 회차를 클릭하면 아래에 표시한다.

- 작품 제목
- 날짜와 시간
- 장소
- **배역별 캐스팅** (배역명과 배우명을 나란히)
- 이벤트 배지 (커튼콜 촬영, 포토타임, 막공, 프레스콜 등)
- 캐스팅 변경 이력 (있을 경우)
- `+ 내 달력에 담기` 버튼
- 이벤트 정보가 비어 있으면 `이벤트 정보 없음 · 제보하기` 버튼

### 6.5 애배

- 최대 4명. 4명이 찬 상태에서는 추가 버튼이 비활성화되고 "애배 자리 없음"으로 표시
- 애배 달력 상단에 배우 칩을 두어 특정 배우만 필터링 가능
- 달력 색은 **계열은 배우, 농도는 작품**으로 배정한다. 한 배우가 두 작품에 동시 출연할 때 같은 계열의 진하기 차이로 구분된다
- 색 규칙 범례를 달력 위에 항상 노출한다

### 6.6 내 달력

- **정의: 예매를 완료한 회차만 담는다.** 관심 표시 용도로 쓰지 않는다
- 이 정의를 흐리지 않는다. 관심 표시가 섞이면 "가고 싶었던 회차"와 "실제로 가는 회차"가 뒤엉켜 확정 일정표로서의 기능이 무뎌진다
- 애배 달력과 내 달력은 시간순으로 역할이 나뉜다. 캐스팅표 공개 직후에는 애배 달력을 보고, 티켓팅 이후에 내 달력이 채워진다

### 6.7 제보

| 제보 유형 | 반영 방식 | 이유 |
| --- | --- | --- |
| 이벤트 정보 | **즉시 반영 + 미검증 배지**, 관리자 승인 시 배지 제거 | 틀려도 손해가 작음. 제보자가 즉시 반영을 보아야 참여 동기가 생김 |
| 캐스팅 오류 정정 | **관리자 승인 후 반영** | 잘못된 캐스팅 정보는 유저가 수만 원짜리 티켓을 잘못 잡게 만든다 |

남용 방지 장치

- 로그인 필수
- 출처 링크 필수
- 같은 회차에 하루 1회로 제한
### 6.8 캐스팅 변경 이력

- 캐스팅을 **덮어쓰지 않는다.** 변경분을 새 레코드로 추가한다
- 예정 캐스팅과 실제 출연을 분리해 보관한다
- 이를 통해 "그날 누가 나왔는지" 조회가 가능하고, 대체 캐스팅 공지도 이력에서 자동으로 생성된다

### 6.9 데이터 모델 스케치

```
works        (id, title, venue, tier)
work_aliases (id, work_id, alias)
roles        (id, work_id, name, order)
actors       (id, name)
castings     (id, work_id, role_id, actor_id)      -- 전체 캐스팅 풀
performances (id, work_id, date, time)
perf_casts   (id, performance_id, role_id, actor_id,
              status,          -- planned | actual | superseded
              changed_at, note)
perf_events  (id, performance_id, label, verified, source_url, reporter_id)
favorites    (user_id, actor_id, order)            -- 최대 4
tickets      (user_id, performance_id)             -- 내 달력
reports      (id, user_id, performance_id, type, payload, source_url, status)
notices      (id, date, tag, text)
```

`works.tier`는 회차별 캐스팅을 정식 지원하는 작품과 일정만 제공하는 작품을 구분하기 위한 값이다. **커버리지를 숨기지 않고 드러내는 것이 신뢰를 만든다.**

### 구분색 팔레트

화면마다 새로 배정한다. 전역 고유색을 두지 않는다. 작품이 수백 개로 늘어나면 색이 모자라기 때문이다.

배정 순서를 고정한다. **보라 → 주황 → 청록 → 자홍 → 올리브 → 파랑 → 갈색 → 회보라**

앞의 네 색이 서로 가장 멀어서, 실제로 가장 자주 발생하는 2~4개 항목 상황에서 확실히 구분된다. 파랑을 보라 바로 뒤에 두지 않은 것이 핵심이다. 두 색은 작은 칩에서 잘 구분되지 않는다.

### 타이포그래피

| 용도 | 폰트 |
| --- | --- |
| 제목 | Gowun Batang (명조) |
| 본문 | Noto Sans KR |
| 날짜·시간·숫자 | IBM Plex Mono (고정폭) |

날짜와 시간에 고정폭 서체를 쓰는 이유는 달력에서 숫자가 세로로 정렬되어야 읽기 쉽기 때문이다.

### 그 밖

- 다크 모드 없음
- 칩은 원형(pill), 선택 시 색으로 채우고 미선택 시 테두리와 점으로 표시
- 색에만 의존하지 않는 경로를 항상 확보한다. 모바일 달력 셀은 탭하면 상세가 열린다

## 8. 제약사항

### 가장 큰 위험

**회차별 캐스팅 데이터를 어디서 확보할 것인가.** KOPIS는 공연 단위 출연진 목록만 제공하고 "8월 15일 윤서는 누구"라는 정보는 주지 않는다. 이 서비스의 핵심 데이터가 자동으로 얻어지지 않는다는 뜻이다.

현재 가정: **제작사 공식 공지를 직접 판독해 수동 입력한다.** 이 가정이 틀리면 프로젝트 구조 전체를 다시 봐야 한다.

### 운영 부담

- 초기 커버리지 목표는 5~10개 작품이나, **5개로 시작해 익숙해진 뒤 늘린다**
- 대극장 작품 하나가 월 30회차 내외. 10개 작품이면 월 300건 입력
- 실제 병목은 입력이 아니라 판독이다. 제작사가 캐스팅표를 이미지로 올리므로 매달 여러 장을 눈으로 읽어 옮겨야 한다
- 캐스팅표 공개 시점이 작품마다 제각각이라 상시 확인이 필요하다
- 가용 운영 시간: 주당 5시간 이상
- **낡은 캐스팅 정보는 없는 것보다 나쁘다.** 유지할 수 없는 커버리지는 늘리지 않는다

### 개발 조건

- 백엔드와 데이터베이스 구현이 처음이다
- 바이브코딩으로 진행한다
- 4~6주를 목표로 하되, 로그인과 제보 시스템이 작업량의 절반 이상을 차지한다는 점을 감안한다
- 일정이 밀리면 잘라낼 순서: 제보 시스템 → 로그인 → 내 달력(브라우저 저장으로 대체)

### 콜드 스타트

차별점 두 가지가 모두 유저 참여에 의존한다. 이는 구조적 약점이다.

대응: **초기 이벤트 정보는 직접 채운다.** 인기작 3~5개의 커튼콜 촬영, 포토타임, 막공 정보를 제작사 공지와 SNS에서 직접 수집해 넣어둔다. 빈 칸만 있는 서비스에는 아무도 제보하지 않는다.

### 재방문 장치 부재

알림을 MVP에서 제외했으므로 유저가 스스로 방문해야 한다. 홈에 배치한 제보·공지 피드가 이 역할을 대신한다. 안정화 이후 캐스팅표 공개 알림을 우선 추가할 것을 권한다.

### 데이터 출처

- 예매처(인터파크 등) 크롤링은 이용약관 위반 소지가 있어 사용하지 않는다
- 공연 일정 기초 데이터는 KOPIS 오픈 API를 사용한다 (2단계)
- 회차별 캐스팅과 이벤트는 제작사 공식 공지를 1차 출처로 한다

## 검증되지 않은 가정

PRD를 진행하되 아래 항목은 실제 확인이 필요하다.

1. 뮤연을 이미 쓰는 사람이 애배력을 추가로 쓸 이유가 충분한가
2. 이벤트 정보를 위해 서비스를 옮길 만큼 그 불편이 큰가
3. 제보를 실제로 하는 사람이 존재하는가 (필요하다고 말하는 것과 실제 행동은 다르다)
4. 주당 5시간의 수동 입력을 몇 달간 지속할 수 있는가

1~3번은 실제 관객 5명에게 물어보는 것으로 상당 부분 확인 가능하다. 물을 때는 "필요하냐"가 아니라 **"마지막으로 커튼콜 촬영이 있는 회차를 어떻게 알았느냐"**처럼 과거 행동을 묻는다.
